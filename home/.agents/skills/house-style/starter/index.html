Build cache/a proposal/example content

One cache, every build.

Every CI job downloads the same dependencies before it does anything useful. One shared, read-only cache would cut a typical build from nine minutes to under five.

01/The problem

Half of every build is a download.

A typical build spends four of its nine minutes fetching packages it fetched an hour ago. Every job starts from an empty disk, so every job pays again, and the queue behind it waits too.

The fix is not a faster network. It is not downloading the same bytes at all.

Illustrative figures for this example/how they were measured

02/The idea

Fetch once, read everywhere.

A cache beside the runners holds every package a build has asked for. Jobs read from it and never write to it, so one bad job cannot poison another's build. Only the cache talks to the registry.

Left: each job pulls the same packages over the network. Right: jobs read a nearby cache they cannot change, and only the cache fetches.

03/What it costs

Small to run, quick to undo.

The cache is one service and a disk per region. Turning it off sends jobs back to the registry, so a bad day costs speed, never correctness.

Why not cache inside each runner

Runners are thrown away after each job, so a local cache starts empty every time. Keeping runners alive to keep their caches would cost more than one shared cache, and would let jobs see each other's leftovers.

04/Where it stands

Two repositories in, three to go.

The pilot runs on the two busiest repositories. The rest move once a week of the pilot shows no wrong builds; each owner only approves the switch.

05/Still open

What I don't know yet, most pressing first.

Two questions decide when the last repositories move. Neither blocks the pilot.

  • Open

    Private registries.

    Search pulls from a registry the cache cannot reach yet. Settled once the registry team grants it read access.

  • Unmeasured

    Disk size per region.

    A week of packages fits today. Settled by a month of growth figures from the pilot.
